## Constats importants

### I1. La précondition « répétition générale enregistrée » est satisfaite par une répétition périmée et n'est liée ni à G ni au gel
- Fichier : `scripts/sealed_evaluation.py:120` (`glob("*-repetition-generale-temps-b.json")`) ; écriture de l'enregistrement : `scripts/sealed_evaluation.py:155-156`.
- Fait constaté : `results/runs/` contient deux runs de ce nom, `20261005-081950-...` (répétition d'avant le gel, système final C2, alors figurant en tête) et `20261006-182842-...` (avec G). Le glob ne distingue pas les deux, et l'enregistrement ne porte ni le système final, ni la référence, ni l'empreinte du fichier de gel (`params` ne contient que `n`).
- Scénario d'échec : on modifie `frozen_final.json` ou le code de `compute`, on n'exécute pas de nouvelle répétition, `check` répond « toutes remplies » grâce au run du 05/10 ; l'ouverture lit alors les étiquettes avec un chemin de calcul jamais répété (une `KeyError` après l'écriture du marqueur consomme le test, voir `sealed.py:86-96`).
- Correctif : enregistrer dans la répétition `final`, `reference`, `secondaires`, le SHA-256 de `frozen_final.json` et celui de `sealed_evaluation.py`/`final_report.py` ; la précondition exige un run dont ces valeurs égalent celles du gel courant et dont la date est postérieure à celle du fichier de gel.

### I2. Le gel n'est pas appliqué à l'ouverture : aucune vérification des empreintes, de la composition, de δ ni de la fiche
- Fichiers : `scripts/sealed_evaluation.py:36-38` (`DELTA`, `ENC_SEEDS`, `LORA_SEEDS` codés en dur), `:105-122` (préconditions), `:169-186` (seuls `final`, `reference`, `secondaires` sont lus dans le gel) ; `src/llmft/freeze.py:30` (empreintes recopiées du registre, jamais recalculées).
- Fait constaté : `frozen_final.json` contient `sha256_modele`, `sha256_temps_a`, `delta`, `composition`, `fiche_modeles_finaux_sha256` ; rien de cela n'est relu par `check` ni par `open`. ADR-016 présente le gel comme figeant ces éléments. Vérification faite par moi à la date de la revue : les sept empreintes de modèles, les sept empreintes de temps A, l'empreinte du gel (`8cb2382c…`, égale à celle d'ADR-016) concordent ; la fiche `2026-10-05-modeles-finaux.md` est inchangée depuis `f195336` (je n'ai pas comparé son hachage au champ `fiche_modeles_finaux_sha256`, qui n'était pas dans ma lecture). Donc aucun défaut effectif, mais aucun garde-fou non plus.
- Scénario d'échec : un fichier `temps_a/lora-s1000.probs.npz` est regénéré (le refus d'écraser porte sur l'existence, pas sur le contenu, et `np.savez_compressed` n'est pas atomique), ou `delta` du gel est changé à 1,5 : `open` ignore le gel pour δ et pour les empreintes et produit un verdict sous un autre critère que celui annoncé.
- Correctif : dans `preconditions()`, (a) recalculer le SHA-256 de chaque `TEMPS_A/{n}.probs.npz` et le comparer à `frozen["modeles"][n]["sha256_temps_a"]` ; (b) exiger `frozen["delta"] == DELTA`, `frozen["composition"]` égale aux constantes du script, et le SHA-256 de la fiche ; (c) comparer le SHA-256 de `frozen_final.json` à la valeur écrite dans `experiments/INDEX.md` ou dans ADR-016. Les élèves distillés (`student-s*`), exigés par `MODEL_NAMES` (`:38`) et rapportés dans `systemes`, ne figurent pas au gel : les y ajouter ou les sortir des préconditions.

### I3. `run_guarded.sh` ne tue que le premier processus : les petits-fils d'un script de lot survivent au garde
- Fichiers : `scripts/run_guarded.sh:48` (`nice ... "$@" &`), `:58` (`kill -TERM "$pid"` seul) ; usage réel : `scripts/chaine_morfitt.sh:7` (`run_guarded.sh bash scripts/run_morfitt.sh`) et les lots lancés « sous `run_guarded.sh` » (fiche `2026-10-06-encodeur-plis-auteurs.md`, N27).
- Scénario d'échec : RAM disponible sous 20 000 Mio pendant `run_encodeur_auteurs.sh` ; le garde envoie TERM au `bash` du lot ; le `timeout 3600 python ...` (petit-fils, via `run_lot` puis `bash -c`) n'est pas dans le processus visé et continue à consommer la mémoire, alors que le garde a écrit « arrêt » dans `memoire.log` et rendu le code 3. C'est exactement l'incident de WSL du 05/10 que le garde est censé prévenir. `mem_guard.sh` (`pkill -P`) gère un niveau de plus, pas `run_guarded.sh`.
- Le test ne mord pas : `tests/test_run_guarded.py:23` n'utilise que `sleep 40`, un binaire direct (N34 demande un cas qui doit mordre ; celui-ci ne peut pas échouer sur ce défaut).
- Correctif : lancer la commande dans son propre groupe (`setsid nice -n ... "$@" &`) et arrêter le groupe (`kill -TERM -- -"$pid"`, puis `-KILL`) ; ajouter un test avec `bash -c 'sleep 40 & wait'` qui vérifie qu'aucun `sleep` ne reste après le code 3.

### I4. Preuve d'identité du tokenizer : deux échantillons non épinglés sans plantage, et le cache est actif dans le script de preuve
- Fichiers : `scripts/tokenizer_identity.py:44` (appel avec le cache par défaut), `:45-47` ; run `20261006-105551-tokenizer-identite-sous-processus-epingle` (`plantages_non_epingle: 0` pour les deux tokenizers) ; `src/llmft/tokenizer_guard.py:1-8` (25 plantages sur 31 runs sans épinglage).
- Constat : la conclusion de Q24, « aucun run passé n'est touché », repose sur la comparaison de la sortie épinglée avec une seule tokenisation non épinglée par modèle, qui a réussi du premier coup alors que le taux historique de plantage est d'environ 80 %. Cet échantillon ne se trouve donc pas dans le régime où la course a lieu. Si la course peut corrompre une tokenisation sans planter (le diagnostic n'exclut pas ce cas : la panique est à `normalizer.rs:373` et l'indice de plantage varie), les runs passés non épinglés et les temps A de l'encodeur, du TF-IDF et des élèves (`20261005-1518` à `1530`, avant la garde) n'ont pas de garantie. Ces six temps A ont été produits sans la garde actuelle, sur les textes du test, avec les copies de tokenizer des dossiers `final-*` ; l'identité n'a été mesurée que sur les textes de développement et sur les noms du hub.
- Aggravant : `isolated_build_inputs(name, texts, max_len)` est appelé sans `cache_dir=None` ; si l'entrée existe déjà au cache, la « sortie épinglée » est lue du disque et la preuve ne teste pas le chemin courant de `run_child`.
- Correctif : relancer la preuve avec `cache_dir=None`, au moins 10 passes non épinglées aboutissant (compter les plantages, comparer chaque passe réussie à la sortie épinglée), et sur les dossiers `final-encoder-s1000` et `final-lora-s1000` ; sinon rétrograder la phrase de Q24 en « identité observée sur deux passes, non démontrée sous course ».

### I5. L'affirmation « tous les textes, développement et test, ont la même fin, un saut de ligne » n'est ni calculée ni cohérente avec `RESULTATS.md`
- Fichiers : `docs/decisions/ADR-016-gel-du-systeme-final.md:17` ; `RESULTATS.md:735` (« les fins de textes ne sont pas fixes (vérifié sur les 3 586 textes : aucun marqueur de fin commun ») ; `scripts/p1_04_06_tfidf.py:29-30` (`patient_text` termine par le texte brut du dernier document, sans saut de ligne imposé).
- Constat : la fin du texte dépend du dernier document, pas de la construction. Le diagnostic montre qu'enlever le saut de ligne final coûte 7,7 points au LoRA (0,7025 contre 0,7795). Aucun script ne compte la part des textes de développement ni de test qui finissent par `\n`. Deux passages du même fichier se contredisent, et l'ADR s'en sert pour écarter le risque sur le test.
- Scénario d'échec : une fraction du test se termine sans `\n` ; le LoRA, donc G, perd plusieurs points sur ce sous-ensemble et l'ADR l'avait écarté sans preuve. Le résultat observé (F 0,8033, au-dessus du développement) rend un effondrement improbable, il ne remplace pas la mesure.
- Correctif : une mesure sans étiquette, journalisée (`sealed_inputs`), de la proportion de textes finissant par `\n` en développement et en test, écrite dans un run ; corriger `RESULTATS.md:735` (ou y renvoyer à la section suivante) pour qu'il n'affirme plus l'absence de marqueur de fin ; reformuler l'ADR avec la proportion mesurée.

### I6. L'accès aux étiquettes du test se fait en dehors de la « porte unique » avant l'écriture du marqueur
- Fichiers : `scripts/sealed_evaluation.py:181-185` (`full_frame()` charge `suggested_scenario` de tous les patients, test compris, puis compare les étiquettes de développement) ; `src/llmft/sealed.py:1` (« Porte unique d'accès ») et `:86-87` (marqueur et journal écrits après).
- Constat : les étiquettes du test sont lues et mises en mémoire, la politique des classes rares est calculée avec les effectifs du test (`full_frame`, `:99`), avant `open_sealed_test`. Aucune fuite n'a eu lieu (rien n'est affiché, la comparaison ne porte que sur le développement), mais le journal d'accès ne reflète pas le moment réel de lecture et un planter entre `:181` et `:187` laisserait une lecture non tracée. Si la politique de classes rares changeait une étiquette de développement, le refus `:184` est correct mais intervient après avoir lu le test.
- Correctif : construire le cadre de développement et un cadre de test séparés, le second seulement dans `sealed_labels_and_score` ; ou, au minimum, écrire la ligne de journal avant `full_frame()`.

## Constats mineurs

### M1. Cache de tokenisation : clé incomplète (périmé possible)
`src/llmft/tokenizer_guard.py:51-56`. La clé contient nom, longueur, versions de `tokenizers` et de `transformers`, empreinte des textes, mais ni le code de `lora_train.truncate_head_tail` / `special_affixes` (qui font partie du résultat mis en cache), ni l'empreinte des fichiers du tokenizer, ni la révision du dépôt (`name` est un identifiant de hub ou un chemin). La limite des fichiers est reconnue dans la docstring (`:62-63`) et Q24 ; celle du code de troncature ne l'est pas. Scénario : un correctif de `truncate_head_tail` ne change aucune clé, les anciens identifiants sont resservis, et `make check` passe (les tests de cache utilisent un faux fils, `tests/test_token_cache.py:14`). Correctif : ajouter à la clé une constante `CACHE_VERSION` incrémentée par le correctif, ou le SHA-256 du source des deux fonctions et de `build_inputs_local`, et l'empreinte (taille et mtime, ou SHA) de `tokenizer.json` du dossier.

### M2. Cache : entrée lue sans validation de forme, et écriture non sûre en concurrence
`src/llmft/tokenizer_guard.py:65-70` (pas de contrôle `len(cached) == len(texts)`, exceptions couvertes limitées à quatre types : un pickle tronqué peut lever aussi `IndexError` ou `TypeError`) ; `:81-83` (le fichier temporaire s'appelle toujours `<clé>.tmp` : deux processus tokenisant les mêmes textes se disputent le même `.tmp`, et le second `replace` lève `FileNotFoundError` après une tokenisation réussie de 75 à 132 s). Correctif : `tempfile.NamedTemporaryFile(dir=cache_dir, delete=False)` ou un suffixe `os.getpid()`, validation de la longueur à la lecture, et un format JSON au lieu de pickle (supprime aussi l'exécution de code à la désérialisation d'un fichier du cache ou du dossier temporaire, risque faible en local).

### M3. Sous-processus sans délai d'attente et relance de tout code non nul
`src/llmft/tokenizer_guard.py:44-46`, `:72-78`. Une course qui bloque au lieu de planter bloque l'appel sans fin (les lots ont `timeout`, pas les appels interactifs ni `sealed_evaluation.py inputs` lancé à la main). Un code 1 d'erreur déterministe (tokenizer introuvable hors ligne, `ValueError` de `special_affixes`) est relancé six fois, soit jusqu'à une dizaine de minutes perdues, et le message final ne garde que 300 caractères de stderr. Correctif : `timeout=` dans `subprocess.run`, ne relancer que les codes 134 et 139 (et les signaux négatifs), laisser remonter les autres immédiatement.

### M4. Appariement du tokenizer parent et du fils par le seul nom
`scripts/p1_finetune.py:39-42`. `build_inputs` ignore l'objet `tok` reçu dès que `name_or_path` est non vide et recharge `AutoTokenizer.from_pretrained(name)` dans le fils. Un tokenizer chargé avec des options (`use_fast`, `fix_mistral_regex` comme dans `measure_token_lengths.py:45`, jetons ajoutés) ou modifié après chargement produirait des identifiants différents sans signal. Aucun appelant actuel du chemin de production n'en passe (vérifié par `grep`), mais rien ne l'interdit. Correctif : comparer dans `build_inputs`, sur une phrase sonde, `tok.encode` du parent et le résultat du fils, ou refuser un `tok` dont `init_kwargs` n'est pas vide.

### M5. Le garde de VRAM de `run_guarded.sh` lit la mémoire de tout le GPU, et se désactive en silence
`scripts/run_guarded.sh:52-56`. `nvidia-smi ... memory.used` inclut les processus que le garde n'a pas lancés (Ollama, règle GPU de CLAUDE.md) : un lot est arrêté à cause d'un voisin. Si `free` ou `nvidia-smi` échoue (`dispo` vide, `[N/A]`), `[ "$dispo" -lt ... ]` erre sans effet et le garde ne mord plus, sans message. Correctif : valider que `dispo` est un entier (sinon alerte et arrêt prudent), interroger `--query-compute-apps` pour le PID gardé et ses fils.

### M6. Le test de statique des redirections ne couvre que `run_*.sh` et un seul motif
`tests/test_lot_scripts_quoting.py:10-15`. `chaine_morfitt.sh`, `mem_*.sh` et `scripts/lib/lot.sh` ne sont pas examinés ; `\d*>>?\s*\$\{?LOGDIR` ne voit pas `> $LOG` ni `> $ROOT/...`. Le chemin du dépôt contient des espaces. Correctif : étendre le glob à `scripts/**/*.sh` et le motif à toute redirection suivie d'un `$` non guillemeté.

### M7. Le signal « TERMINE » ne signifie pas « réussi », et la chaîne peut attendre sans fin
`scripts/run_encodeur_auteurs.sh:16` écrit `TERMINE` même si des `run_lot` ont renvoyé `ECHEC` ; `scripts/chaine_morfitt.sh:6` boucle `until grep -q "TERMINE (graines : 1 2)"` sans délai : si la règle d'arrêt anticipé (N31) écarte les graines 1001 et 1002, ou si le lot est interrompu, l'ancrage MorFITT n'est jamais lancé. Correctif : écrire `TERMINE` seulement si tous les codes sont nuls (sinon `TERMINE_AVEC_ECHECS`), et borner l'attente par un délai.

### M8. `encoder_author_analysis.py` : constantes sans `run_id`, réfèrence d'ensemble différente, graines mal nommées
`scripts/encoder_author_analysis.py:96-98` (0,7202, 0,7598, 4,6 recopiés à la main, alors qu'ils existent au registre : règle « un chiffre sans `run_id` n'existe pas » et risque de dérive) ; `:115` (les graines sont déduites par `glob` : la mesure `results/measures/encoder_author_analysis.json` rapporte `graines: [0]`, c'est-à-dire la graine 1000, et compare une seule graine à une référence qui est une moyenne de trois graines, ce qui biaise la « perte » dans le sens défavorable : la fiche prévoit trois graines des deux côtés) ; `:119-127` (échoue seulement par `FileNotFoundError` si un pli manque une graine, ce qui est le bon comportement, mais l'état actuel du dépôt, avec `pli0-s2.out` sans prédictions, le ferait échouer). Correctif : lire les valeurs de référence dans les `metrics` des runs correspondants, imposer le même nombre de graines que la référence (ou calculer la référence à la même graine), écrire les graines réelles (1000 + k).

### M9. `prune_analysis.py` : ordre des classes des bras non vérifié, et analyse de latence retirée du script
`scripts/prune_analysis.py:50-54` : `labels` est pris du bras `plain` et les étiquettes des autres bras (`loaded[...][2]`) sont ignorées ; un bras entraîné avec un autre ordre de classes serait agrégé sans erreur. Correctif : `assert` d'égalité des listes d'étiquettes entre bras. Séparément, le bloc de latence a été retiré du script (le diff le supprime) ; la latence reste au run `latence-encodeur-elague`, donc pas de perte de preuve, mais `results/measures/prune_analysis.json` ne contient plus `latence_ms_p50`, que d'anciens documents ont pu citer : à vérifier.

### M10. `budget.py` : plantage possible sur `params: null`, et sous-comptage non déclaré
`src/llmft/budget.py:17-18` : `record.get("params", {})` renvoie `None` si la clé existe avec une valeur nulle, d'où `AttributeError` (idem pour `metrics`). Le budget ne compte que `seconds_train` et `seconds_tokenize` : l'inférence (temps A, robustesse, diagnostics de 25 minutes de GPU), les runs ayant planté sans être enregistrés et les reprises ne sont pas dans les « 46 h sur 90 » ; ce nombre est donc un minorant et doit être dit tel. ### M11. Divers
- `tests/test_tokenizer_guard.py:72` : `skipif` hors Linux. Le plancher interdit les tests sautés sans raison écrite ; la raison est écrite (`reason=`) et l'environnement est Linux, mais le code de production (`tokenizer_child.py:9`) ignore l'épinglage en silence hors Linux : la protection disparaît sans message. La répétition ne couvre que les étiquettes de développement. - `scripts/robustness_lora_diag.py:167` et `robustness_learned.py:84` : le JSON de mesure est écrit même sans `--register` et écrase le précédent ; sans effet sur le registre, mais un rejeu accidentel remplace la mesure citée.
